# Field

`<craft-field>` is the shell that puts Craft's standard field chrome around a control.

<Canvas of={FieldStories.Default} sourceState="shown" />

Label, instructions, tips, warnings, errors, and the status badge all come from the field. The control it wraps supplies only itself.

## What It Does Not Do

The shell never touches the slotted control's value, validation, or events. It provides the chrome and the label/description ARIA wiring, and nothing else.

That is what makes it general: any control can go in the `input` slot — a Craft component or a plain `<input>` — and get the same field treatment without the field knowing anything about it.

<Canvas of={FieldStories.WithCraftInput} sourceState="shown" />

## Custom Controls

The field gives its label, instructions and errors to the control in the `input` slot, so a screen reader announces them when the control takes focus. How it does that depends on the control:

- **A native control** (`<input>`, `<select>`, `<textarea>`) gets the field's `<label>` and an `aria-describedby`.
- **A Craft form control**, such as `craft-input` or `craft-select`, or a control that extends one, is handed the field's label, `help-text` and `feedback` elements, and attaches them to the element that takes focus.
- **Any other control** isn't changed. The field gives itself `role="group"` and names that instead.

The group fallback suits a control that is really several inputs, such as a set of checkboxes. Build a single custom control by extending the Craft control it's a variation of, as [Select Color](?path=/docs/form-controls-select-controls-select-color--docs) extends `craft-select-rich`, or only its own label and description are announced.

## Instructions, Tips, and Warnings

Three different things, rendered differently on purpose:

- **`help-text`** — how to fill the field in. Always visible, below the label.
- **`tip`** — supplementary advice, in an info callout.
- **`warning`** — a consequence worth knowing before changing the value, in a warning callout.

## Errors

Errors render in the `feedback` slot and are wired to the control with `aria-describedby`, so they are announced when the control takes focus rather than only being visible beside it.

The status badge marks a field whose value is outdated or overridden. The translation indicator marks a field whose value is per-site, with `translation-description` explaining the scope.

## Fieldsets

<Canvas of={FieldStories.FieldsetMode} sourceState="shown" />

`fieldset` renders the shell as a `<fieldset>` with a `<legend>` instead of a label bound to one control.

Use it when the field holds several controls that share one question — a group of checkboxes, a date and time pair. A `<label>` can only point at one control, so a group needs a legend.

## Actions

<Canvas of={FieldStories.Actions} sourceState="shown" />

The `actions` slot holds field-level controls: a hide-label toggle, a copy-value button, a settings menu.

`label-extra` does something similar and is **deprecated** — use `actions`.

## In PHP

In a Craft control panel screen, or a plugin's `settingsUi()`, describe the UI with `CraftCms\Cms\Ui\Ui` instead of writing markup.
`CraftCms\Cms\Ui\Nodes\Field` renders a field around a control:

```php
use CraftCms\Cms\Ui\Controls\Choice;
use CraftCms\Cms\Ui\Controls\Text;
use CraftCms\Cms\Ui\Enums\ChoicePresentation;
use CraftCms\Cms\Ui\Enums\FieldWidth;
use CraftCms\Cms\Ui\Nodes\Field;
use CraftCms\Cms\Ui\Ui;

Ui::make([
    Field::make('Title', Text::make('title'))
        ->required()
        ->instructions('What this entry will be called in the control panel.')
        ->tip('Titles appear in search results.')
        ->width(FieldWidth::Half),
    Field::make('Status', Choice::make('status')
        ->presentation(ChoicePresentation::Radios)
        ->options([
            ['label' => 'Live', 'value' => 'live'],
            ['label' => 'Disabled', 'value' => 'disabled'],
        ]))
        ->fieldset(),
]);
```

The control's path names its input, and validation errors for that path are shown on the field.
`instructions()`, `tip()`, `warning()`, `required()`, and `translatable()` set the parts of the same names.
Call `fieldset()` when the control is a group of inputs, such as radio buttons, so the label becomes the group's legend.
`actions()` adds nodes next to the label, such as a [Copy Attribute](?path=/docs/components-copy-attribute--docs) or an [Action Menu](?path=/docs/components-action-menu--docs).

## Accessibility

The field is where a control's accessible name and description come from, which makes it the single most load-bearing component in a form.

- **Every control in a form belongs in one.** A bare input has no name; wrapping it is the cheapest way to fix that.
- **Use `fieldset` for groups.** A label pointing at the first of five checkboxes names that checkbox, not the group.
- **Build custom single controls on a Craft control.** Otherwise the field can only name a group around them, and focusing the control doesn't announce the label, instructions or errors. See [Custom Controls](#custom-controls).
- **`required` is announced,** not just marked with a symbol — so a person hears the requirement rather than needing to see the asterisk. The field marks the control its label names `aria-required="true"`, so there's no need to set it on the control. In `fieldset` mode it can't tell which controls are required, so mark those yourself.
- **Keep the label visible.** Set `label` on every field, and only use `label-sr-only` when the control's purpose is obvious without it, such as a search box beside its button.
- **Set `readonly` and `disabled` on the control too.** The field doesn't pass those down, so put them on the control as well as the field. That way the control itself is announced as read-only or unavailable.
- **Errors need text.** Put the messages in the `feedback` slot.
- **Say how to fix it.** "Enter a date after the start date" helps; "Invalid value" doesn't.
- **Move focus on submit.** When a form fails validation, move focus to the first invalid control. The field won't move focus for you.
