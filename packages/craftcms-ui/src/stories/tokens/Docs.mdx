# Variants & Appearances

The component system uses two independent properties to control how semantic color is applied to UI elements:

- **Variant** - _What kind of message is this?_ Values: `neutral`, `success`, `warning`, `danger`, `info`
- **Appearance** - _How prominently should it be displayed?_ Values: `solid`, `fill`, `outline-fill`, `outline`, `plain`

Any variant can be combined with any appearance. A `danger` callout can be a bold `solid` banner or a subtle `plain` inline hint. The variant stays the same; the appearance controls how loudly it speaks.

---

## How variants work

Setting `variant="danger"` on a component remaps a set of **generic** CSS custom properties to the corresponding **semantic group** tokens. Components author their styles against the generic tokens, so they never need to know which color group is active.

```css
[variant='danger'] {
  --c-color-fill-loud: var(--c-color-danger-fill-loud);
  --c-color-fill-normal: var(--c-color-danger-fill-normal);
  --c-color-fill-quiet: var(--c-color-danger-fill-quiet);
  --c-color-border-*: var(--c-color-danger-border- *);
  --c-color-on-*: var(--c-color-danger-on- *);
}
```

This indirection happens in `src/styles/variants.styles.ts`, a shared Lit CSS module that any component can import.

## Using in a new component

### 1. Import the shared variant styles

Components supporting variants should import `variants.styles.ts` to get the standard variant-to-token mapping:

```ts
import {LitElement, css, type CSSResultGroup} from 'lit';
import {property} from 'lit/decorators.js';
import variantsStyles from '@src/styles/variants.styles.js';
import {Variant, type VariantKey} from '@src/types';

export default class MyComponent extends LitElement {
  static override styles: CSSResultGroup = [variantsStyles, styles];

  @property({reflect: true})
  variant: VariantKey = Variant.Neutral;
}
```

### 2. Author styles against generic tokens

Write your component CSS using the generic `--c-color-*` custom properties. The variant mapping fills these in automatically:

```css
:host {
  background-color: var(--c-color-fill-normal);
  border: 1px solid var(--c-color-border-normal);
  color: var(--c-color-on-normal);
}
```

### 3. Color one region instead of the whole component (optional)

Every rule in `variants.styles.ts` matches two ways: `:host([variant~='…'])`,
which is the case above, and `[data-variant~='…']`, which any element inside
your shadow root can ask for by attribute:

```ts
html`<div class="callout__action" data-variant=${this.variant}></div>`;
```

That's the shadow-DOM twin of the `[data-palette]` rules in
`shared/colorable.css`, which only reach light DOM. The tokens are ordinary
custom properties, so a region set this way overrides the palette it inherits
from the host — and a region that should stay neutral while the host is
coloured can say `data-variant="neutral"`.

### 4. Add appearance support (optional)

If your component needs multiple visual intensities, add an `appearance` property and style each level:

```ts
import {Appearance, type AppearanceKey} from '@src/types';

@property({reflect: true})
appearance: AppearanceKey = Appearance.Fill;
```

```css
:host([appearance~='accent']) {
  background-color: var(--c-color-fill-loud);
  border-color: var(--c-color-border-loud);
  color: var(--c-color-on-loud);
}

:host([appearance~='plain']) {
  background-color: transparent;
  border-color: transparent;
  color: var(--c-color-on-quiet);
}
```

### Key conventions

- **Reflect properties** - both `variant` and `appearance` should use `reflect: true` so they appear as HTML attributes for CSS matching.
- **Use `~=` selectors** - appearance selectors in existing components use `[appearance~='value']` (word matching) rather than `[appearance='value']` (exact matching).
- **Default to neutral** - set sensible defaults (`Variant.Neutral` / the most common appearance) so components look correct without explicit attributes.
- **Define custom subsets when needed** - if the standard `Variant` or `Appearance` type doesn't fit (like Button's `primary` variant), define component-specific values instead of forcing the shared types.

## Using tokens from Tailwind

The CP's stylesheet turns Craft's design tokens into utility classes, and sets
Tailwind's `prefix(cp)` so that **everything Tailwind generates is prefixed
`cp:`** — Craft's token utilities and stock Tailwind alike:

```html
<div
  class="cp:flex cp:gap-2 cp:bg-danger-normal cp:text-on-danger-normal"
></div>
```

That gives one namespace for the whole utility system, and makes anything
unprefixed recognisable as a legacy class from the old SCSS bundle.

The prefix is `cp` rather than `c` on purpose. Under `prefix(c)` Tailwind
renames its own theme variables into `--c-*`, which is Craft's token namespace,
and eight of them — `--c-text-sm`, `--c-radius-sm`, `--c-font-mono` and
friends — would land on Craft tokens of the same name holding different values.
With `cp`, Tailwind's variables sit at `--cp-*` and nothing overlaps.

### Colors

Color utilities read as `cp:<property>-[group-]<strength>`. A token's _role_
is implied by the property rather than repeated in the class name — `fill`
paints backgrounds, `border` paints borders, and `on` paints the text that sits
_on_ a fill:

| Utility                   | Token                           |
| ------------------------- | ------------------------------- |
| `cp:bg-danger-normal`     | `--c-color-danger-fill-normal`  |
| `cp:border-accent-quiet`  | `--c-color-accent-border-quiet` |
| `cp:text-on-neutral-loud` | `--c-color-neutral-on-loud`     |
| `cp:text-neutral-loud`    | `--c-color-neutral-fill-loud`   |

Text is the one property that takes two roles. `cp:text-*` inks with the fill
color, for text that carries the color itself; `cp:text-on-*` inks with the
color meant to stay legible _against_ that fill, for text sitting on top of it:

```html
<!-- danger-colored text on the page background -->
<p class="cp:text-danger-loud">Something went wrong</p>

<!-- text on a danger-colored fill -->
<div class="cp:bg-danger-loud cp:text-on-danger-loud">Something went wrong</div>
```

Omit the group and you get the generic tokens, which is usually what you want
inside a component: `cp:bg-quiet`, `cp:border-normal`, and `cp:text-on-loud`
paint with whatever the nearest palette or `variant` resolved to, rather than
naming a color up front.

`cp:border-*` sets `border-color` only, exactly as Tailwind's own color
utilities do — pair it with `cp:border` for a width.

Scope is deliberately narrow: the six semantic groups plus the generic tokens.
The raw palette (`--c-color-red-*` and friends) is still reachable from CSS and
from a palette selector, it just doesn't get utility classes.

### Palette selectors

`cp-palette-*` puts an element — and everything under it — into a color group,
remapping the generic tokens to that group's:

```html
<div class="cp-palette-danger">
  <!-- cp:bg-quiet is now danger's quiet fill -->
  <span class="cp:bg-quiet cp:text-on-quiet">…</span>
</div>
```

Note the single dash: this is a plain stylesheet rule, not something Tailwind
generates, so it carries no `cp:` prefix and works in the legacy shell and
inside shadow roots too. `[data-palette='danger']` does the same thing from an
attribute, for markup that is easier to set programmatically. The Craft 5
spellings `.cp-color-*` and `[data-color]` still work and resolve to the same
rule.

This is a different axis from `[data-theme='dark']`, which selects the
light/dark color scheme — which is why the palette attribute isn't called
`data-theme`.

### Spacing

Spacing reads as `cp:<stem>-<step>` across padding, margin, and gap. The stems
match Tailwind's own, so `cp:px-*` is logical (`padding-inline`) and `cp:pl-*`
is physical:

| Token             | Utilities                             |
| ----------------- | ------------------------------------- |
| `--c-spacing-sm`  | `cp:p-sm`, `cp:gap-sm`, `cp:mx-sm`, … |
| `--c-spacing-2xl` | `cp:p-2xl`, `cp:mt-2xl`, …            |
| `--c-spacing-1px` | `cp:p-1px`, `cp:gap-1px`, …           |

The numeric scale is untouched — `cp:p-4` still resolves through Tailwind's own
spacing base. The scale's `--c-spacing` base gets no utilities of its own: it's
the unit the named steps multiply, not a step you'd reach for on an element.

### How it's wired up

`resources/css/utilities.css` is the entry that sets the prefix and pulls in
the token values, Tailwind, and Craft's utilities. **Both CP shells load it** —
the Inertia shell through `cp.css`, and the legacy Twig shell on its own via
`CpAsset` — so a `cp:` class means the same thing on either side, and the
`--c-*` tokens that the legacy stylesheet's compatibility aliases resolve
against are actually defined there.

```css
@layer theme, utilities;

@import 'tailwindcss/theme.css' layer(theme) prefix(cp);
@import 'tailwindcss/utilities.css' layer(utilities);

@import '@craftcms/ui/styles/shared/variables.css' layer(theme);
@import '@craftcms/ui/styles/shared/tokens.css' layer(theme);
@import '@craftcms/ui/styles/shared/colorable.css' layer(theme);

@import '@craftcms/ui/tailwind.css';
```

That last import takes no `layer()`: `@utility` may not be nested, and a
layered import would nest it. Tailwind places what it generates into the
`utilities` layer regardless.

The utilities reference the `--c-*` custom properties rather than snapshotting
their values, so `[data-theme='dark']` overrides and palette context both flow
through them untouched.

`tailwind.css` is generated by `scripts/generate-tailwind.js` (colors come
from `src/constants/colors.data.ts`, the same source as `shared/colorable.css`),
so adding a semantic color there gives you its utilities for free. Don't edit
it by hand.

### Legacy classes

The old SCSS bundle ships utility classes of its own, and two of them share a
name with a Tailwind utility while meaning something different:

| Class         | Legacy definition                                            |
| ------------- | ------------------------------------------------------------ |
| `hidden`      | `display: none !important` — Tailwind's has no `!important`  |
| `inline-flex` | also sets `align-items`, `align-content` and `gap: var(--s)` |

These stay unprefixed on purpose, so they keep resolving to the legacy rule.
Reach for `cp:hidden` / `cp:inline-flex` only when you specifically want
Tailwind's plainer version.
