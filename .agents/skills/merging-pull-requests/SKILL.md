# Merging pull requests

When explicitly instructed to merge a PR, follow the path below. It also applies when there are no conflicts, such as when GitHub only blocks the merge because the current head's required checks are missing after `[ci skip]` commits. Resolve conflicts in the final merge commit into the PR's actual target branch if every conflict is either:

- Inconsequential and nonfunctional, such as overlapping `CHANGELOG.md` entries.
- A generated build artifact that can be regenerated from merged sources with the appropriate documented build script. Regenerate outputs; do not hand-merge generated content.

Do not merge the target branch into the PR or rebase and push the PR merely to resolve these conflicts and trigger repeated PR CI. Judge the conflicting content, not just the filename. Ask for confirmation before resolving substantive source or dependency conflicts, or any other conflicts outside these categories. Eligibility for build artifact regeneration does not make behavior-changing artifacts eligible for `[ci skip]` or nonfunctional-only CI inheritance.

For this path:

1. Fetch the latest PR head and actual target branch. Confirm that the PR head has passed all required CI, or use earlier successful required CI for agent pre-merge verification only if the tested commit is an ancestor of the current PR head, every subsequent PR commit ends its body with `[ci skip]` (before any trailers), and inspection of every subsequent commit plus the complete cumulative diff from the tested commit to the current head confirms genuinely nonfunctional-only changes under the CI skip marker eligibility rules in `AGENTS.md`. Required approvals must remain satisfied for the current PR state. When using inherited CI, report both the tested SHA and current-head SHA; never claim the current head itself passed. Check the target's branch protections, required merged-result checks, and merge queue requirements before pushing. When inherited CI is valid under these conditions, nothing relevant has changed since the tested commit, so do not wait for or trigger a rerun of the head's required checks. With explicit authorization to merge the PR and only conflicts eligible under this policy, an ordinary push of the final target-based merge commit may use the credential's existing bypass permission for the PR-only rule and for the required status checks that the inherited CI covers, after the CI verification and current-state approval checks above. Never bypass failed required checks, required checks that inherited CI doesn't cover, fresh merged-result checks, merge queues, or any other protection. Do not use an administrative override, such as `gh pr merge --admin`. If another protection prevents this path or compliance is unclear, stop and ask how to proceed.
2. Use a clean worktree based on the fetched target commit, then run `git merge --no-ff --no-commit <verified-pr-head-sha>`. Resolve only the eligible conflicts covered above, preserving both sides' intended content, including changelog entries and release ordering. For generated build artifact conflicts, run the appropriate documented build script on the merged sources.
3. Inspect the staged merge result and the complete diff against the target. Validate the resolved documentation and inspect regenerated outputs. Check for leftover conflict markers and run `git diff --cached --check`. These lightweight checks do not validate the substantive merged result. Run applicable build verification and tests for regenerated artifacts, plus all required tests and merged-result verification for the PR's substantive changes; passing or inherited PR CI does not replace required merged-result checks.
4. Before committing and pushing, confirm that the PR head is still the verified commit and that CI verification and current-state approvals remain valid. If the head changed, restart with the latest head and repeat those checks. Commit the merge and use an ordinary push to the actual target branch, never a force-push. If the target advances before the push succeeds, discard the unpublished merge, fetch the latest heads, and repeat from a clean worktree based on the latest target, including inspection and required validation.
5. If the PR changed any file in `resources/translations/`, run the translation sync after the merge is pushed, so the changes reach the translation catalog and the other branches: `gh workflow run translation-sync.yml -R craftcms/cms --ref translations`. Watch the run with `gh run watch`, and report any `t9n/<branch>` pull requests it opens or updates.
